## 1. 境目の形（実際の Swift を読んで確かめた）
- 記録の正本は、画面（WebView）の中の保存だけ：自分用は IndexedDB（前は localStorage）。
- Swift（`app/ios/App/App/WidgetBridgePlugin.swift`・`KurashiWidget.swift`・`MainViewController.swift`）は記録を持たない。持つのは記録から作った写しだけ。
  - ウィジェットの要約（App Group の UserDefaults）
  - 自動バックアップ（書類フォルダ。14日分と、記録がいちばん多かったときの控え）
  - iPhone のカレンダーの「くらしベース」
  - 通知（ID が `kb|` で始まるもの）
- アプリから画面へ記録を戻す道はない。
  - 自動バックアップから戻すのは、本人が設定の「バックアップから復元」で選んだときだけ。
  - 文字の読み取り（OCR）の結果は、入力画面の候補になるだけ。保存は本人が押す。
  - アプリの部品とやり取りする画面（取り込み・WidgetSync・iPhone の連携・通知）は、記録を書き換える `useStore` を使わない。

## 4. 直さずに記録だけするもの（低）
- 記録がいちばん多かったときの控え（`kurashi-base_largest_backup.json`）は、件数が減っても更新されない。わざとまとめて消したあとも、古い控えが残る。
- 小さいウィジェットには「更新」の時刻が出ない。
- 通知の時刻は、登録した時点の時差で決まる（旅先ではアプリを開き直すまで元の時差）。
- .ics の書き出しの UID は名前から作るので、200文字を超える名前の予定は、前のファイルと UID が変わる。
- Swift 6 の言語モードにすると、通知の数え方の書き方で組み立てが通らないおそれがある（今は 5.0）。
- localStorage と IndexedDB が一緒に消えると、何も知らせずに空で始まる。自動バックアップは残る。
- 「記録がない状態から始める」のあと、復元より先に記録を足すと、その日の自動バックアップのファイルが上書きされる。記録がいちばん多かったときの控えは残る。
- 「記録がない状態から始める」のあとも、古い記録は元の場所（localStorage）に残り、診断の「保存の大きさ」に出る。すべて削除で消える。
