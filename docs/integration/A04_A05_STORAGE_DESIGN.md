# A04・A05 保存の作り直し（設計。o11 工程3）

状態：**設計のみ。実装していない。** 保存先の切り替えは、利用者のデータに直接かかわるので、試験の道具（下の「承認が要るもの」）と、実機での確認がそろってから行う。

## 1. 今（A01 の棚卸しより）
- Web も iPhone も、WebView の localStorage の1つのキー（`kurashi-base:data:v1`）に全データ。保存は同期（すぐ結果が返る）。
- 取り消し用の控え（UNDO_KEY）を書く操作は、データの約3.2倍の容量を使う（RAID R-06）。
- iPhone は Capacitor 8.6.0（`capacitor://localhost` の WKWebView）。ネイティブ側の保存は、毎日のバックアップのファイル（writeBackup）だけで、記録の正本ではない（feat/ios-widget の Swift を確認）。

## 2. 決めたこと（案）
- **正本は1つ**：Web と iPhone の両方で、WebView の IndexedDB を正本にする（ネイティブの SQLite との二重の正本はつくらない）。iPhone のファイルのバックアップは、今までどおり控え。
- **Repository の境界**：画面と store は「Repository」（読み込み・保存・控え・取り消し）だけを通す。実体は2つ：
  1. LocalStorageRepository（今の storage.ts を包むだけ。動きは変えない）
  2. IndexedDbRepository（新しく作る）
- **原子的な保存**：IndexedDB の1つの readwrite のトランザクションで「版（revision）の照合 → 本体の書き込み → 取り消し用の差分の書き込み」を行う。トランザクションが完了したときだけ、画面に「保存しました」を出す。失敗したら、入力は画面に残す。
- **保存は非同期になる**：今の store の操作（addTx など）は、結果をすぐ返す作り。IndexedDB にすると、すべての操作が「待ってから結果」になる。画面の約40か所の呼び出しを、順に直す（大きな変更。A06 と一緒に行う）。

## 3. 移行（A05）の手順
1. 旧データ（localStorage）を読む → `validateAppData` で検査。壊れていたら移行しない（今までの退避の仕組みを使う）。
2. 移行の前に、旧データのバックアップを、別のキー（または iPhone はファイル）に残す。
3. 新しい DB に「仮置き（staging）」として書く → 読み直して、件数・金額の合計・関連 ID（固定費・旅行・返金・目標）を旧データと比べる。
4. 一致したときだけ、正本を新しい DB に切り替える（切り替えの印を新しい DB に書く）。**旧データは消さない**。
5. 途中で落ちても、印がなければ旧データのまま起動する（何度でもやり直せる）。
6. 旧版のアプリが起動したとき：旧データ（localStorage）を読むので、移行後に足した記録は見えない。→ 移行後は、旧データ側に「この端末は新しい保存に移りました」の印を書き、旧版では書き込みを止める（新しい記録を失わないため）。旧形式への書き戻しは、新しい記録を失わないときだけ。
7. 複数のタブ：IndexedDB の版の照合で、古いタブの保存を止める（今の conflict と同じ考え）。

## 4. 試験の計画
- 単体：保存・取り消し・版の照合・失敗の注入（書き込み中の例外・容量不足）・移行の途中停止と再実行・件数/金額の比較。
- ブラウザ：実際の IndexedDB で、移行→再読込→記録の追加→取り消し→再読込。複数タブ。
- iPhone 実機：移行・アプリの再起動・OS の容量不足時の動き（未確認の項目）。
- 30年相当の合成データで、移行の時間と容量。

## 5. 承認が要るもの
- 単体試験で IndexedDB を使うための `fake-indexeddb`（開発用の npm パッケージ。アプリ本体には入らない）。npm の追加は、本人の OK が要る（PJ_RULES）。なければ、ブラウザの画面での試験だけになり、失敗の注入が難しい。
- 公開版（友人β）の保存の切り替え：友人の端末のデータにかかわるので、公開の判断と一緒に別に決める。まずは自分用の版だけで切り替える。
