# A06 画面の金額を共通台帳へ（o11 工程4）と v22 G0 の復元の往復

状態：**実装・独立点検（3回）・回帰試験まで済み。iPhone 実機での確認は未（A08）。**
コミット：22ecf27（実装）→ 06a1acb・c8e1e72（1回目の点検の直し）→ 1e8f802（2回目の点検の直し）。`npm run check` 669件合格。

## 1. 何を変えたか
- 画面に出る金額は、すべて `lib/ledgerCore.ts` の「収支に数える出来事」（`ledgerEntries`・`txEntries`・`sumEntries`・`isLifeExpense`）から作る。
  - 切り替えた所：月・日（`aggregate.ts`）、期間・週・年（`periods.ts`）、月の内訳（`monthBreakdown.ts`）、週の見直し（`weeklyReview.ts`）、振り返りの気づき（`report.ts`）、月末の見込みとグラフ（`forecast.ts`）、復元の確認の合計（`restoreView.ts`）、旅行につないだ支出（`app/trips`）、履歴の絞り込みの合計（`app/history`）
  - 関数の名前と戻り値の形は変えていない。`forecastMonthEnd` に、省いてよい3つ目の引数 `life` を足した（グラフで台帳を2回作らないため。今それを渡しているのは `forecastCurve` だけ）
- ウィジェットのプレビューの「今月の残り予算」は、自分用の版で、ホームと同じ数え方（投資を除いた生活費。`budgetSpent`）になった。前は投資も入れて引いていたので、ホームと数字が違っていた（独立点検 中2）
- 保存の形は変えていない（`types.ts`・`schema.ts`・`storage.ts` は変更なし）

## 2. 確かめ方（`app/tests/`）
- `a06-ledger-screens.test.ts`
  - 切り替える前の実装の写し（`tests/legacy/`）と、200通りの合成データ（`tests/fixtures/synth.ts`）で、すべての集計を比べて同じ答えになる
  - 画面どうしの一致（日の合計＝月＝年の月＝期間＝週の区切り、生活費＋投資＝支出、月末の見込み＝その月の生活費、など）
  - 手で決めた期待値（全額返金・一部返金・投資の分け方・日付の境界）
  - 見張り：`app/src` 全体で、金額を足す書き方を、ファイルごとの行数で固定する
- `a06-personal.test.ts`：自分用の版として動かしたときの比べ（振り返りの気づき、ホームとウィジェットの予算の比べ方）
- `a06-perf.test.ts`：1.5万件で、前の実装と交互に測る。上限は前の実装の1.5倍＋2ms。今は前と同じか速い（年の画面：新 27.6〜29.3ms、旧 31.0〜32.0ms）
- `backup-roundtrip.test.ts`（v22 G0）
  - 書き出し → 読み込み → 置き換え／追加で復元 → 保存（localStorage・IndexedDB）→ 開き直し → 取り消し。中身（`toStrictEqual`）とお金の答えが同じ
  - 保存に失敗したとき（IndexedDB の書き込みの失敗・localStorage の容量不足）は、開いている画面・取り消しの控え・開き直したデータが、前のまま
  - 別のタブで先に保存されていたら、古い画面からの復元は保存しない
  - v1 のバックアップも戻せる。書き換えたファイルは読み込まない

## 3. 残っている低（記録だけ。直さない理由つき）
- 見張りの漏れ：空白のない `s+t.amount`、複数行に分けた reduce の最後の行、変数に入れてから足す形、引き算は拾わない。また、許可した行を同じ数のまま書き換えても気づかない。書き方の見張りであって、台帳を通っていることそのものの証明ではない。新旧の比べと、画面どうしの一致の試験で補っている
- 型の外れた記録（type が expense でも income でもない）は、前後で数え方が変わる。ただし読み込みの検査（`schema.ts`）が弾くので、保存されたデータでは起きない
- 新旧の比べは、`classify.ts`・`date.ts`・`allowance.ts` を共有している。共通の部分のバグは、比べでは見つからない（手で決めた期待値の試験と、golden fixture で補う）
- 容量不足の試験は、すべての書き込みを失敗させている。「控えは書けたが本体で失敗し、控えを戻す」道は `tests/data-protection.test.ts` で確かめている（StoreCore を通した形ではない）
- 速さの試験の上限は、旧が 2〜3ms の集計では余裕が大きい（今の新の約2倍まで遅くなっても通る）
