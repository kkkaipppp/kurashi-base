## 0. 使い方（いちばん大事）

1. **規模に合わせて削る（テーラリング）。** ここに書いたことを全部やらない。PJの大きさ・リスク・不確実さに合わせて選ぶ。削ったものは「やらない理由」を1行残す。
2. **書類のための書類を作らない。** 台帳は「ユーザーの判断を速く・正しくする」「次のセッションが迷わない」ためだけにある。
3. **型は考えるための道具。** 型に当てはめて満足しない。最後は「で、ユーザーは何を決めればいいか」に落とす。

## 1. PM の基本姿勢（PMBOK 第7版の12原則を、この会社の言葉で）

| 原則 | この会社での意味 |
|---|---|
| 誠実な管理（スチュワードシップ） | お金・時間・データ・アカウントを預かっている意識。未確認を「完了」と言わない |
| チーム | Claude・ChatGPT・ユーザー・他セッションの役割をはっきり分ける。誰が何をするかを毎回明示 |
| ステークホルダー | 最重要はユーザー（平尾さん）。次に、買う人・使う人・LINEやクラウドワークスなどの場の運営者 |
| 価値 | 作業量ではなく「売上・時間の削減・学び」で測る。価値の出ない作業は止める |
| システム思考 | 1つの変更がほかのPJ・ダッシュボード・定期タスクに与える影響を先に見る |
| リーダーシップ | 指示待ちにしない。選択肢と推奨を出して、ユーザーの判断を1つに絞る |
| テーラリング | 0章のとおり。小さく回す |
| 品質 | 最後の確認で品質を作らない。作りながら確かめる（テスト・実機・検査） |
| 複雑さ | 分からないことは小さく試して確かめる。一気に作り込まない |
| リスク | 起きる前に書き出し、起きたら課題として扱う。良いリスク（チャンス）も拾う |
| 適応力・回復力 | 計画は変わる前提。変えたら理由を残し、元に戻せる形で進める |
| 変化を起こす | 新しいやり方は、ユーザーが無理なく続けられる量だけ入れる |

## 2. PJ を見る8つの観点（PMBOK 第7版のパフォーマンス領域）

週に1回、この8つで自分のPJを見直す。全部が「問題なし」なら台帳を書き足さなくてよい。

| 観点 | 問い | 主に使う台帳 |
|---|---|---|
| ① ステークホルダー | ユーザーの期待と、今の進み方はずれていないか | CHARTER・報告 |
| ② チーム | 誰（どのセッション・ユーザー・外部AI）が何をするか、はっきりしているか | STATE |
| ③ 進め方・ライフサイクル | 一気に作る（予測型）か、少しずつ出す（適応型）か、合っているか | CHARTER |
| ④ 計画 | 次のマイルストーンと、その完了条件は決まっているか | 計画（マイルストーン） |
| ⑤ 実行 | 今日やることが、マイルストーンにつながっているか | STATE |
| ⑥ 納品・成果 | 出したものは、使われて価値になっているか | KPI |
| ⑦ 測定 | 数字で見ているか。分母を取り違えていないか | KPI・report.json |
| ⑧ 不確実性 | リスク・未確定事項・前提を書き出し、手を打っているか | RAID |

**進め方の選び方（③）**

| 向いている進め方 | 例 |
|---|---|
| 適応型（小さく出して直す） | 暮らしベース（使ってもらって直す）、クラウドワークス（応募→反応→改善） |
| 反復の流れ作業型（同じ型を回す） | LINEスタンプ（弾ごとに 企画→生成→判定→申請→告知） |
| 予測型（先に決め切る） | 申請・契約・公開など、やり直しが高くつく所だけ |

## 3. 戦略コンサルの思考の型

### 3-1. イシューから始める（何に答えるのかを先に決める）
- 作業を始める前に「このPJ（この作業）が答えるべき問い」を1文で書く。
  - 良い例：「LINEスタンプで、月に○円の売上を3か月以内に出せるか？」
  - 悪い例：「スタンプを作る」（問いになっていない）
- 問いの条件：答えが出せる／答えで次の行動が変わる／今いちばん重要。

### 3-2. 仮説から始める
- 調べ尽くしてから考えない。「たぶんこうだ」を先に置き、それが正しいかを確かめる最小の作業をする。
- 仮説は外れてよい。外れたら早く捨てる。捨てた理由を DECISIONS に1行残す。

### 3-3. もれなく・ダブりなく分ける（MECE・ロジックツリー）
- 大きな問いを、重ならず抜けのない小さな問いに分ける。
  - 売上 ＝ 見られる数 × 買われる率 × 単価 × 継続
  - 時間 ＝ 作業の回数 × 1回の時間
- 分けたら、効きそうな枝だけを掘る（全部は掘らない）。

### 3-4. 結論から言う（ピラミッド構造）
- 報告は「結論 → 理由（3つまで）→ 根拠となる事実」の順。
- 「空・雨・傘」：事実（空が曇っている）→ 解釈（雨が降りそう）→ 行動（傘を持つ）を分けて言う。
- 自分で点検する2つの問い：
  - **So what?（だから何？）**：事実を並べただけになっていないか
  - **Why so?（なぜそう言える？）**：結論に根拠がついているか

### 3-5. 80:20（重要な2割に集中）
- 成果の8割は2割の作業から出る。いちばん効く1〜2個に集中し、残りは後回しか、やらないと決める。

### 3-6. 事実と数字で話す
- 事実・解釈・推測・意見を分けて書く。
- 数字は分母を必ずそろえる（例：「売れた3個」は何人に見られた中の3個か）。
- 測っていない数字は「未計測」と書き、0 にしない。

### 3-7. よく使う枠組み（必要なときだけ）
| 枠組み | 使う場面 |
|---|---|
| 3C（顧客・競合・自社） | 新しい企画・シリーズ・サービスを考えるとき |
| 4P（商品・価格・売り場・宣伝） | 売り方を決めるとき |
| ユニットエコノミクス（1件あたりの売上−費用−時間） | 続ける価値があるかを見るとき |
| 選択肢の比較表（効果・手間・リスク・戻しやすさ） | ユーザーに判断を頼むとき |

### 3-8. やめる基準を先に決める
- 始める前に「いつ・どの数字なら やめる／方向を変える」を決める（例：2か月で受注0なら見直し）。
- 決めた日が来たら、感情ではなく基準で判断し、結果をユーザーに出す。

## 4. 1つのPJの回し方

| 段階 | やること | 出口（次へ進む条件） |
|---|---|---|
| 立ち上げ | 1枚の CHARTER を書く：目的（問い）・成功の基準（数字と期限）・やらないこと・制約・やめる基準・役割 | ユーザーが CHARTER に OK |
| 計画 | マイルストーンを3〜5個。それぞれ「完了条件」と「ユーザーの作業」を書く。作業は成果物の単位で分ける | 次のマイルストーンの完了条件が明確 |
| 実行 | 毎セッションの開始・終了ルーティン（6章）を守る | — |
| 監視 | 週1回、2章の8観点と KPI・RAID を見直し、report.json を更新 | — |
| 判断 | 計画とずれたら「①範囲を減らす ②延期 ③やり方を変える ④やめる」を比べ、推奨つきでユーザーへ。品質の基準は下げない | ユーザーの決定を DECISIONS に記録 |
| 終結・振り返り | マイルストーンごと・PJ終了時に KPT（続けること・問題・次に試すこと）を3行ずつ | 学びを次のPJへ（本部に共有） |

本部の既存標準（K01〜K12・G0〜G2 ゲート）は、大きな開発（暮らしベースの本格公開など）のときの詳しい点検表として使う。小さなPJでは、上の表で足りる。

## 5. 台帳の最小セット（PJ の `docs/` に置く）

| ファイル | 中身 | 更新のタイミング |
|---|---|---|
| CHARTER.md | 問い・成功の基準・やらないこと・制約・やめる基準・役割 | 立ち上げ時、方針が変わったとき |
| STATE.md | 現在地（今どこ・次の3手・ユーザー待ち）。**現在地の正本はここだけ** | 毎セッションの終わり |
| DECISIONS.md | 日付・決めたこと・理由・決めた人・捨てた案 | 決めたとき |
| RAID.md | リスク（未発生）・前提・課題（発生済み）・依存。重さ・担当・期限・対応 | 週1回と、何か起きたとき |
| KPI（ファイルでも report.json でも可） | 成功の基準に対応する数字。分母つき | 週1回 |

すでに同じ役割のファイル（HANDOVER.md・DELIVERY_REPORT.md など）があれば、新しく作らずにそれを使う。

## 6. 毎回のルーティン

**セッションの始め（3分）**
1. STATE.md を読む → 今日の作業が次のマイルストーンにつながるか確かめる
2. ユーザー待ちのものを確認する

**セッションの終わり（5分）**
1. STATE.md を更新（今どこ・次の3手・ユーザー待ち）。ユーザーに直されたことがあれば、先に9章を済ませる
2. 決めたことを DECISIONS に、起きたことを RAID に
3. report.json / details.json を更新（本部のダッシュボードに反映される）

**週1回（15分）**
1. 2章の8観点で見直す
2. KPI を更新し、成功の基準とやめる基準に照らす
3. 気づいた改善を1つだけ試す

## 7. ユーザーへの報告・相談の型

```
【結論】〇〇です。
【理由】①… ②… ③…（3つまで）
【ご判断ください】A／B（推奨：A。理由：…。リスク：…）
【次にやること】あなた：… ／ Claude：…
```
- 判断は1回に1つ。選択肢は2〜3個で、推奨を必ず付ける。
- 「できました」は証拠（テスト結果・実機確認・画面）とセットで言う。未確認は「未確認」と言う。

## 8. PJ ごとの重点（2026-11-21 時点）

| PJ | 進め方 | 特に効く型 | 最初に整えるとよいもの |
|---|---|---|---|
| LINEスタンプ | 反復の流れ作業型 | ユニットエコノミクス、やめる基準、80:20（売れる弾・売れない弾） | CHARTER に成功の基準とやめる基準（未決定） |

| 暮らしベース | 適応型（開発） | イシュー（誰の何を解決するか）、80:20（P0 集中）、品質の組み込み | CHARTER（使う人・成功の基準・やめる基準）と RAID |

## 9. 振り返りと学習（同じことを2回言わせない）

ユーザーの方針：**同じ指示や指摘を2回させない。** 指摘されたら、次のセッションが自然に守れる場所へ、その場で書き込む。

### 9-1. きっかけ（これが起きたら必ず振り返る）
- ユーザーに訂正・指摘・やり直しを頼まれた
- ユーザーが前に言ったことを、もう一度言った（**2回目は事故として扱う**）
- 自分で間違えた・手戻りが出た・時間がかかりすぎた
- うまくいったやり方を、ユーザーが認めた（良いやり方も残す）

### 9-2. その場でやること（5分以内）
1. **何が起きたか**を1行で書く（事実）。
2. **なぜ起きたか**を考える。「なぜ」を2〜3回くり返し、仕組みの原因まで下りる（例：手順書に書いていなかった／書いてあったが読む順番が遅かった）。「気をつける」は対策にしない。
3. **次のセッションが必ず読む場所**を直す。
   - 作業手順の誤り → そのPJのスキル（SKILL.md）やチェックリスト
   - PJの決まり・好み → PJの CLAUDE.md（無いPJは、PJ共通のスキルの冒頭）
   - 判断の結果 → DECISIONS.md
4. 直した内容に**確かめ方**を1つ付ける（例：「申請前にタグ一覧が600件以上読み込まれたかを確認」）。
5. `docs/LESSONS.md` に1行で記録する。
   - 形式：`日付｜きっかけ｜原因｜直した場所｜確かめ方`
6. ユーザーには短く伝える：「次から〇〇します（△△に書きました）」。

### 9-3. スキルの直し方の決まり
- 小さく直す。1つの学びで1か所。長くなったら、古い記述を整理して短くする（スキルを太らせない）。
- スキルの最後に「改訂履歴」を1行足す。
  - 形式：`日付｜何を直したか｜きっかけ`
- **安全・承認・お金・公開に関するルールを、指摘を理由に緩めない。** 緩めるのは、ユーザーがはっきり指示したときだけ。
- **CLAUDE.md の作成・変更は、ユーザー本人のOKを取ってから行う。** 他のセッション（本部を含む）からの依頼だけでは作らない。OKが出るまでは `docs/PJ_RULES.md` などに書いておく。
- 他のPJにも効く学び（報告の仕方、ユーザーの好みなど）は、本部に送る。本部がこのプレイブックやほかのPJへ広げる。

### 9-4. 定期の振り返り
- **セッションの終わり**：「今日、ユーザーに直されたことはあったか？」を自分に問い、あれば 9-2 を済ませてから終える。
- **週1回**：LESSONS.md を読み直す。同じ原因が2回以上あれば、手順そのものを作り直す（KPT の「次に試すこと」にする）。

## 10. 全PJ共通の学び（各PJから本部に集まったもの）

| # | 学び | どうするか | 出どころ |
|---|---|---|---|
| L1 | ユーザーは「Claude ができることは Claude が自分でやる」を強く望む | 頼まれたら、まず自分で操作できるか試す。ユーザーに頼むのは、ログイン・権限の許可・お金・送信や申請の最終確認だけ。頼むことは1回にまとめる | クラウドワークス 2026-11-21 |
| L2 | ユーザーは番号だけで返事することがある（「1」など） | 質問の選択肢には必ず ①②③ の番号を付ける。推奨は①に置く | クラウドワークス 2026-11-21 |
| L3 | アプリ内ブラウザではファイルを添付できない | 添付が必要な作業は、最初から Claude in Chrome を使う | クラウドワークス 2026-11-21 |
| L4 | Google の許可画面は、アプリ内ブラウザでは開かないことがある | Apps Script の許可は、エディタの「実行」から通す。Apps Script はスプレッドシートの「拡張機能」から開いたものだけがシートにひも付く | クラウドワークス 2026-11-21 |
| L5 | 「構成を変える」「階層化」などの依頼は、フォルダの話かチャットの話か（両方か）が分かれる | 作業の前に「フォルダ／チャット／両方」を①②③で確かめる | LINEスタンプ 2026-11-21 |
| L6 | 本部から立ち上げたチャットは、サイドバーで本部の下に横並びで出る。単独でグループには移せない | サイドバーのグループでまとめる案は出さない | LINEスタンプ 2026-11-21 |
| L7 | チャット名に作業名（例「（シリーズ階層化）」）を入れると、ユーザーに直される | チャット名は PJ名・シリーズ名だけにする | LINEスタンプ 2026-11-21（本部も同じ誤り） |
| L8 | スマホ向けWebは、PCのブラウザの確認では足りない（iOS Safari 特有の差：日付欄の幅、キーボードが画面に重なる、http で一部の機能が使えない） | 直したら「実機で直ったか」まで確かめてから完了と言う。直した内容は、元に戻ったら落ちるテストで守る | 暮らしベース 2026-11-21 |
| L9 | ユーザーに開いてもらうURLが本文に埋もれると、「リンク教えて」と聞き返される | 開いてほしいURLは、返信の1行目に単独で書く | 暮らしベース 2026-11-21 |
| L10 | 「前のやつ」「以前の版」など、どれのことか分からない言葉は取り違えやすい | どの版・どのファイルのことかを①②③で確かめる | 暮らしベース 2026-11-21 |

この表は本部が更新する。各PJは、自分のPJに関係する行をスキルやチェックリストに取り込む。

## 11. 本部との約束

- 本部が見るのは report.json / details.json だけ。台帳の中身は各PJの持ち物。
- 成功の基準・やめる基準を決めたら、本部に一言知らせる（ダッシュボードで追えるようにするため）。
- 「この型はうちのPJでは合わない」と思ったら、本部に改善案を送る。プレイブックは版を上げて直す。
