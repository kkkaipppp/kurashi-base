## 0. 使い方（いちばん大事）

1. **規模に合わせて削る（テーラリング）。** ここに書いたことを全部やらない。PJの大きさ・リスク・不確実さに合わせて選ぶ。削ったものは「やらない理由」を1行残す。
2. **書類のための書類を作らない。** 台帳は「ユーザーの判断を速く・正しくする」「次のセッションが迷わない」ためだけにある。
3. **型は考えるための道具。** 型に当てはめて満足しない。最後は「で、ユーザーは何を決めればいいか」に落とす。
4. **ユーザーに作業を頼む前に、10章の L1・L3 を読み直す。** 自分（Claude in Chrome を含む）でできることを、ユーザーの作業にしない（2026-11-26 お金の仕組みPJ提案）。

## 1. PM の基本姿勢（PMBOK 第7版の12原則を、この会社の言葉で）

| 原則 | この会社での意味 |
|---|---|
| 誠実な管理（スチュワードシップ） | お金・時間・データ・アカウントを預かっている意識。未確認を「完了」と言わない |
| チーム | Claude・ChatGPT・ユーザー・他セッションの役割をはっきり分ける。誰が何をするかを毎回明示 |
| ステークホルダー | 最重要はユーザー（平尾さん）。次に、買う人・使う人・LINEやクラウドワークスなどの場の運営者 |
| 価値 | 作業量ではなく「売上・時間の削減・学び」で測る。価値の出ない作業は止める |
| システム思考 | 1つの変更がほかのPJ・ダッシュボード・定期タスクに与える影響を先に見る |
| リーダーシップ | 指示待ちにしない。選択肢と推奨を出して、ユーザーの判断を1つに絞る |
| テーラリング | 0章のとおり。小さく回す |
| 品質 | 最後の確認で品質を作らない。作りながら確かめる（テスト・実機・検査） |
| 複雑さ | 分からないことは小さく試して確かめる。一気に作り込まない |
| リスク | 起きる前に書き出し、起きたら課題として扱う。良いリスク（チャンス）も拾う |
| 適応力・回復力 | 計画は変わる前提。変えたら理由を残し、元に戻せる形で進める |
| 変化を起こす | 新しいやり方は、ユーザーが無理なく続けられる量だけ入れる |

## 2. PJ を見る8つの観点（PMBOK 第7版のパフォーマンス領域）

週に1回、この8つで自分のPJを見直す。全部が「問題なし」なら台帳を書き足さなくてよい。

| 観点 | 問い | 主に使う台帳 |
|---|---|---|
| ① ステークホルダー | ユーザーの期待と、今の進み方はずれていないか | CHARTER・報告 |
| ② チーム | 誰（どのセッション・ユーザー・外部AI）が何をするか、はっきりしているか | STATE |
| ③ 進め方・ライフサイクル | 一気に作る（予測型）か、少しずつ出す（適応型）か、合っているか | CHARTER |
| ④ 計画 | 次のマイルストーンと、その完了条件は決まっているか | 計画（マイルストーン） |
| ⑤ 実行 | 今日やることが、マイルストーンにつながっているか | STATE |
| ⑥ 納品・成果 | 出したものは、使われて価値になっているか | KPI |
| ⑦ 測定 | 数字で見ているか。分母を取り違えていないか | KPI・report.json |
| ⑧ 不確実性 | リスク・未確定事項・前提を書き出し、手を打っているか | RAID |

**進め方の選び方（③）**

| 向いている進め方 | 例 |
|---|---|
| 適応型（小さく出して直す） | 暮らしベース（使ってもらって直す）、クラウドワークス（応募→反応→改善） |
| 反復の流れ作業型（同じ型を回す） | LINEスタンプ（弾ごとに 企画→生成→判定→申請→告知） |
| 予測型（先に決め切る） | 申請・契約・公開など、やり直しが高くつく所だけ |

## 3. 戦略コンサルの思考の型

### 3-1. イシューから始める（何に答えるのかを先に決める）
- 作業を始める前に「このPJ（この作業）が答えるべき問い」を1文で書く。
  - 良い例：「LINEスタンプで、月に○円の売上を3か月以内に出せるか？」
  - 悪い例：「スタンプを作る」（問いになっていない）
- 問いの条件：答えが出せる／答えで次の行動が変わる／今いちばん重要。

### 3-2. 仮説から始める
- 調べ尽くしてから考えない。「たぶんこうだ」を先に置き、それが正しいかを確かめる最小の作業をする。
- 仮説は外れてよい。外れたら早く捨てる。捨てた理由を DECISIONS に1行残す。

### 3-3. もれなく・ダブりなく分ける（MECE・ロジックツリー）
- 大きな問いを、重ならず抜けのない小さな問いに分ける。
  - 売上 ＝ 見られる数 × 買われる率 × 単価 × 継続
  - 時間 ＝ 作業の回数 × 1回の時間
- 分けたら、効きそうな枝だけを掘る（全部は掘らない）。

### 3-4. 結論から言う（ピラミッド構造）
- 報告は「結論 → 理由（3つまで）→ 根拠となる事実」の順。
- 「空・雨・傘」：事実（空が曇っている）→ 解釈（雨が降りそう）→ 行動（傘を持つ）を分けて言う。
- 自分で点検する2つの問い：
  - **So what?（だから何？）**：事実を並べただけになっていないか
  - **Why so?（なぜそう言える？）**：結論に根拠がついているか

### 3-5. 80:20（重要な2割に集中）
- 成果の8割は2割の作業から出る。いちばん効く1〜2個に集中し、残りは後回しか、やらないと決める。

### 3-6. 事実と数字で話す
- 事実・解釈・推測・意見を分けて書く。
- 数字は分母を必ずそろえる（例：「売れた3個」は何人に見られた中の3個か）。
- 測っていない数字は「未計測」と書き、0 にしない。

### 3-7. よく使う枠組み（必要なときだけ）
| 枠組み | 使う場面 |
|---|---|
| 3C（顧客・競合・自社） | 新しい企画・シリーズ・サービスを考えるとき |
| 4P（商品・価格・売り場・宣伝） | 売り方を決めるとき |
| ユニットエコノミクス（1件あたりの売上−費用−時間） | 続ける価値があるかを見るとき |
| 選択肢の比較表（効果・手間・リスク・戻しやすさ） | ユーザーに判断を頼むとき |

### 3-8. やめる基準を先に決める
- 始める前に「いつ・どの数字なら やめる／方向を変える」を決める（例：2か月で受注0なら見直し）。
- 決めた日が来たら、感情ではなく基準で判断し、結果をユーザーに出す。

## 4. 1つのPJの回し方

| 段階 | やること | 出口（次へ進む条件） |
|---|---|---|
| 立ち上げ | 1枚の CHARTER を書く：目的（問い）・成功の基準（数字と期限）・やらないこと・制約・やめる基準・役割 | ユーザーが CHARTER に OK |
| 計画 | マイルストーンを3〜5個。それぞれ「完了条件」と「ユーザーの作業」を書く。作業は成果物の単位で分ける | 次のマイルストーンの完了条件が明確 |
| 実行 | 毎セッションの開始・終了ルーティン（6章）を守る | — |
| 監視 | 週1回、2章の8観点と KPI・RAID を見直し、report.json を更新 | — |
| 判断 | 計画とずれたら「①範囲を減らす ②延期 ③やり方を変える ④やめる」を比べ、推奨つきでユーザーへ。品質の基準は下げない | ユーザーの決定を DECISIONS に記録 |
| 終結・振り返り | マイルストーンごと・PJ終了時に KPT（続けること・問題・次に試すこと）を3行ずつ | 学びを次のPJへ（本部に共有） |

本部の既存標準（K01〜K12・G0〜G2 ゲート）は、大きな開発（暮らしベースの本格公開など）のときの詳しい点検表として使う。小さなPJでは、上の表で足りる。

## 5. 台帳の最小セット（PJ の `docs/` に置く）

| ファイル | 中身 | 更新のタイミング |
|---|---|---|
| CHARTER.md | 問い・成功の基準・やらないこと・制約・やめる基準・役割 | 立ち上げ時、方針が変わったとき |
| STATE.md | 現在地（今どこ・次の3手・ユーザー待ち）。**現在地の正本はここだけ** | 毎セッションの終わり |
| DECISIONS.md | 日付・決めたこと・理由・決めた人・捨てた案 | 決めたとき |
| RAID.md | リスク（未発生）・前提・課題（発生済み）・依存。重さ・担当・期限・対応 | 週1回と、何か起きたとき |
| KPI（ファイルでも report.json でも可） | 成功の基準に対応する数字。分母つき | 週1回 |

すでに同じ役割のファイル（HANDOVER.md・DELIVERY_REPORT.md など）があれば、新しく作らずにそれを使う。

## 6. 毎回のルーティン

**セッションの始め（3分）**
1. STATE.md を読む → 今日の作業が次のマイルストーンにつながるか確かめる
2. ユーザー待ちのものを確認する

**セッションの終わり（5分）**
1. STATE.md を更新（今どこ・次の3手・ユーザー待ち）。ユーザーに直されたことがあれば、先に9章を済ませる
2. 決めたことを DECISIONS に、起きたことを RAID に
3. report.json / details.json を更新（本部のダッシュボードに反映される）

**週1回（15分）**
1. 2章の8観点で見直す
2. KPI を更新し、成功の基準とやめる基準に照らす
3. 気づいた改善を1つだけ試す

## 7. ユーザーへの報告・相談の型

```
【結論】〇〇です。
【理由】①… ②… ③…（3つまで）
【ご判断ください】A／B（推奨：A。理由：…。リスク：…）
【次にやること】あなた：… ／ Claude：…
```
- 判断は1回に1つ。選択肢は2〜3個で、推奨を必ず付ける。
- 「できました」は証拠（テスト結果・実機確認・画面）とセットで言う。未確認は「未確認」と言う。

## 9. 振り返りと学習（同じことを2回言わせない）

ユーザーの方針：**同じ指示や指摘を2回させない。** 指摘されたら、次のセッションが自然に守れる場所へ、その場で書き込む。

### 9-1. きっかけ（これが起きたら必ず振り返る）
- ユーザーに訂正・指摘・やり直しを頼まれた
- ユーザーが前に言ったことを、もう一度言った（**2回目は事故として扱う**）
- 自分で間違えた・手戻りが出た・時間がかかりすぎた
- うまくいったやり方を、ユーザーが認めた（良いやり方も残す）
- 同じ依頼を3回された（断り続けるのではなく、その場で「決まりを見直すか」を①②でユーザーに聞く）
- 同じ種類の取り次ぎ・依頼が3回続いた（その仕事を、頼む側のPJへ移す案を出す。L28）

### 9-2. その場でやること（5分以内）
1. **何が起きたか**を1行で書く（事実）。
2. **なぜ起きたか**を考える。「なぜ」を2〜3回くり返し、仕組みの原因まで下りる（例：手順書に書いていなかった／書いてあったが読む順番が遅かった）。「気をつける」は対策にしない。
3. **次のセッションが必ず読む場所**を直す。
   - 作業手順の誤り → そのPJのスキル（SKILL.md）やチェックリスト。スキルの無いPJは `docs/制作チェックリスト.md` のような常設のチェックリストを作る。**ずっと守る決まりを STATE の「次の一手」に置かない**（片付けたときに一緒に消える）
   - 機械で確かめられる決まり → 点検の道具・試験にする（例：画像に注意書きを入れない → 点検スクリプト）
   - PJの決まり・好み → PJの CLAUDE.md（無いPJは、PJ共通のスキルの冒頭）
   - 判断の結果 → DECISIONS.md
4. 直した内容に**確かめ方**を1つ付ける（例：「申請前にタグ一覧が600件以上読み込まれたかを確認」）。
5. `docs/LESSONS.md` に1行で記録する。
   - 形式：`日付｜きっかけ｜原因｜直した場所｜確かめ方`
   - 原因の欄の先頭に分類の札を付ける：`［確認なし］［見本の量］［操作］［思い込み］［決まりの置き場所］［道具の癖］［依頼の重なり］` など（9-4 で数えるため）
   - **うまくいったことも記録する**：番号を `K-01` のようにして、`日付｜何をしたか｜なぜ効いたか｜根拠` の形で書く
6. ユーザーには短く伝える：「次から〇〇します（△△に書きました）」。

### 9-3. スキルの直し方の決まり
- 小さく直す。1つの学びで1か所。長くなったら、古い記述を整理して短くする（スキルを太らせない）。
- スキルの最後に「改訂履歴」を1行足す。
  - 形式：`日付｜何を直したか｜きっかけ`
- **安全・承認・お金・公開に関するルールを、指摘を理由に緩めない。** 緩めるのは、ユーザーがはっきり指示したときだけ。
- **CLAUDE.md の作成・変更は、ユーザー本人のOKを取ってから行う。** 他のセッション（本部を含む）からの依頼だけでは作らない。OKが出るまでは `docs/PJ_RULES.md` などに書いておく。
- **ルールは「範囲」と「理由」を添えて書く。** 「絶対に〇〇しない」だけだと、関係のない作業まで控えてしまう。「〇〇のときは、△△のため、許可を得てから行う」の形にする。承認が要る操作は「本番データの削除」のように具体的に書く。
- **月1回、古くなった決まりを消す。** スキル・PJ_RULES・LESSONS を読み直し、理由がなくなった注意書きを消す（消したことは改訂履歴に1行）。安全・承認・お金・公開のルールは、この手入れでは消さない。
- 他のPJにも効く学び（報告の仕方、ユーザーの好みなど）は、本部に送る。本部がこのプレイブックやほかのPJへ広げる。

### 9-4. 定期の振り返り
- **セッションの終わり**：「今日、ユーザーに直されたことはあったか？」を自分に問い、あれば 9-2 を済ませてから終える。
- **週1回**：LESSONS.md を読み直す。同じ原因（同じ札）が2回以上あれば、手順そのものを作り直す（KPT の「次に試すこと」にする）。
- **古くなった質問を取り下げる**：答えのない①②を返事に載せ直す前に、まだ要るかを確かめる。要らなければ「取り下げ」と書く。

## 12. 頼み方・進め方の追加の型（v1.3）

### 12-1. 聞かずに進めてよい作業・承認が要る作業
ユーザーの待ち時間を減らすため、線引きをはっきりさせる。

| 区分 | 作業 |
|---|---|
| 聞かずに進めて、報告で伝える | PJフォルダの中のファイルの作成・編集、テストの実行、ローカルでのコミット、ローカルのサーバーの起動、台帳と報告の更新、下書きの作成、読むだけの調査、同じ操作のやり直し、Claude が自分で作ったテスト用データと一時ファイルの片付け（ごみ箱へ移す。2026-11-22 ユーザー決定） |
| 承認を取ってから行う | 外部への公開、第三者への送信・応募・申請、支出、契約や本番の権限、機密・個人データの外部利用、消す・元に戻せない操作（ユーザーのデータ、ユーザーが作ったファイル、完全に消す操作を含む）、push、ライブラリの追加（npm・pip など）、外部からの大きなダウンロード（評価用のデータなど）、CLAUDE.md の作成・変更、成功の基準とやめる基準の変更 |

迷ったら承認が要る側として扱う。誰が作ったか分からないファイルは、ユーザーのものとして扱う。この表は、承認の範囲を広げるものではない。

### 12-2. 返事が要らない部分は先に進める
ユーザーに質問したら、答えを待つ間に、答えに左右されない作業を進める。質問は1回にまとめ、「待っている間に〇〇を進めます」と添える。

### 12-3. 範囲を小さく絞る・頼まれていない追加をしない
- 1回の依頼では、頼まれた変更と、そのために必要な変更だけを行う。思いついた機能は足さずに、提案として書き留める。
- 機能を足す前に「成功の基準に効くか」を確かめる。効かないなら、後回しの一覧に入れる。
- 成功の基準に期限があるときは、期限から逆算して「機能を足すのを止める日」を決める。

### 12-4. 形をそろえたい文章は、見本を3つ用意する
応募文・告知文・報告のように、何度も書く文章は、良い見本を3つ選んで手元に置き、同じ形と口調で書く。見本は、反応が良かったものに入れ替えていく。入れ替えの判断に使う数字は、PJの KPI から1つ決めておく（例：LINEスタンプは告知のリンクのクリック数、クラウドワークスは応募への返信の有無）。

### 12-5. 一時ファイルを片付ける
試しに作ったファイル、バックアップ（.bak など）、古いレビュー用の ZIP は、区切りごとに片付ける。片付けるのは Claude が自分で作ったものだけで、ごみ箱へ移す（12-1）。移す前に、要るものが混ざっていないかを見て、移したものを報告する。ユーザーに渡したファイル・ユーザーが作ったファイル・迷うものは、動かさずにユーザーへ聞く。

### 12-6. 外部AI（ChatGPT）によるレビュー
ChatGPT のレビューが要るPJは、今のやり方を続ける（2026-11-22 ユーザー決定）。

### 12-7. ファイル名は一意にする（2026-11-22 ユーザー指示）
私たちやツールが作るファイル、ほかの AI（ChatGPT など）に作らせるファイルは、名前だけで「どのPJの・何の・どの版か」が分かり、ほかのファイルとぶつからないようにする。「submit.zip」「preview.png」「output.json」のような、毎回同じになる名前は使わない。
- 形：`<PJ>_<対象>_<内容>_<版か日付>.<拡張子>`。例：`line_kawaii-busho-vol12-naoe_submit_v1.zip`、`cw_13600172_application_20261123.md`。区切りは `_`、語の中は `-`。日付は `YYYYMMDD`。
- ほかの AI に作らせるときは、依頼文でファイル名を指定する。指定どおりでなければ、受け取ったときにこの形へ直す。
- ほかの AI に作らせるファイルの名前には、依頼の版（依頼文の版か日時）も入れる。「v1」と決め打ちにすると、同じものを頼み直したときに前の出力と同じ名前になり、古いファイルを取り違える（2026-11-23、ユーザーの2回目の指摘）。例：`line_kawaii-busho-vol01-nobunaga-o3_submit_v1.zip`（o3＝依頼文の3版目）。
- 同じ名前のファイルがすでにあれば、上書きせずに版を上げる。
- 各PJは、自分の対象の書き方（例：シリーズ・弾・武将ID）を PJ_RULES かスキルに1行で決める。
- 例外：ツールや外部サービスが名前を決めているもの（`report.json`・`details.json`・`CLAUDE.md`・`SKILL.md`・`package.json` など）は、そのままにする。フォルダで区別できていれば足りる。
- すでにあるファイルの名前を変えるのは、Claude が作ってPJの中だけで使っているものなら進めてよい（報告で伝える）。ユーザーに渡したファイル、ユーザーが作ったファイル、ほかのツールが名前で読んでいるファイルは、承認を取ってから変える。

### 12-8. モデルの使い分け（2026-11-24 ユーザー指示）
- 普段は Sonnet で作業する。特に重くない作業（普段の開発・取り次ぎ・検索・下書き）は Sonnet のまま進める。
- 重い場面に入るときだけ、返信の最初に「ここは Opus か Fable 推奨（理由を1行）」と書く。Claude が自分でモデルを切り替えない。切り替えるかはユーザーが決める。
- 重い場面：お金・契約・規約・詐欺の見極め／フォルダやチャットの大きな組み替え／後から直しにくい設計（データの持ち方・公開前の安全確認など）／商標・権利の確認。

### 12-9. 記号と名前（2026-11-25 ユーザー指示「混同しない命名に」）
- **S0/S1/S2 は Venture OS の安全区分だけに使う**：S0＝情報のみ、S1＝隔離したローカルの道具、S2＝承認・セキュリティ・権限などの核心の変更（自動で昇格・正式採用させない。S1 の隔離が保証できなければ自動昇格を止める）。
- **版の比較は「基準・現行・候補」（BASE / CURRENT / CANDIDATE）と呼ぶ。** S0/S1/S2 と書かない。候補は、基準・現行との照合とユーザーの承認なしに正本にしない。現行が新しければ現行を優先し、変更の根拠と履歴を残す。
- **指摘の重さは「重大・高・中・低」か「指摘1・指摘2…」の番号で書く。** S1〜S3 や P0〜P3 のような、ほかの仕組みと同じ記号を重さに使わない（PJ の既存の区分で、すでに意味が決まっているものは除く。その場合は PJ_RULES に定義を1行書く）。
- A1〜A5（承認が要る行為の区分）、P1〜P6（成果物から市場までの判定段階）も、それぞれの意味だけで使う。


### 12-10. 見た目の制作物の手順（2026-11-26、資料工房・受託デスク・動画メディア・お金の仕組みの振り返りから）
画像・動画・資料・スタンプなど、見た目で判断される物を作るPJ向け。
1. **見本を見る量を決める**：伸びている作り手を5人前後・作品30本以上、画面で実物を見て、型（構図・文字の量・色・引き）を要素ごとに数えて書く。見た日付を残す。
2. **案は複数**：方向の違う案を小さく作る（2〜3案。量産する物は5案から別の目の採点で上位2案）。違いを1行ずつ書いて並べ、選んでもらう。
3. **1本で確かめてから広げる**（L25）：選ばれた型で1本だけ仕上げ、ユーザーの OK のあとで横に広げる。
4. **作ったら送る**（L26）。点検の合格だけで渡さない。見た目の OK はユーザーが出す。
5. 叩き台：`資料工房/docs/画像制作の手順.md`。
- 確かめ方：調べのファイルに実物を見た日付と本数がある／渡す前にユーザーに見せた記録がある。

### 12-11. 本部からPJへの依頼文の型（2026-11-26、スタンプ工房・暮らしベースの提案）
- 依頼文に「CLAUDE.md に書く場合は、そのPJのチャットでユーザー本人の OK をもらってから」を必ず書く（9-3）。依頼文に「CLAUDE.md か引き継ぎ書に」とだけ書くと、OK なしで書かれる。
- 返事を求める依頼には「コミット番号は git log から写す」（L20）を1行入れる。
- ユーザーの言葉を伝えるときは、言葉のまま引用し、どのチャットで言ったかを書く。判断の答えを届けるときは 12-14 の形にする（その形で届いた答えは、ユーザーの答えとして扱う）。それ以外の伝言は、承認の代わりにならない。

### 12-12. 予約タスクの型（2026-11-26、家探しの提案）
- 最後に、書いたファイルがあることを確かめ、ローカルでコミットする。
- 同じ日のファイルがすでにあれば、上書きせず「追加分」として書き足す。
- 本部の週1回の点検で、途中で止まって終わった回（「interrupted」など）を拾い、担当のPJに知らせる。

### 12-13. 「もう寝る」と言われたら（2026-11-26 ユーザー指示）
ユーザーが「もう寝る」（「寝る」「仕事に行く」なども同じ）と言ったら、それは「一人でできる作業を進めて」という意味。
- 本部は、稼働中の全チャット（`CHAT_DIRECTORY.md`）に同時に伝える。
- 各PJは、12-1 の「聞かずに進めて、報告で伝える」作業だけを進める。承認が要る作業（公開・送信・支出・契約・消す・push・ライブラリの追加・CLAUDE.md の変更など）はしない。準備だけして、12-14 の判断待ちの一覧に入れる。
- 各PJは振り返りを行う（9章）：
  1. 反省点を LESSONS に書き出す。
  2. 必要な学びは、そのPJのスキルか PJ_RULES に入れて、確かめ方を付ける。
  3. 全PJに広げたい学びは、本部に送る。
- 本部は、届いた学びをまとめる。必要ならプレイブックの版を上げて、全チャットへ配る。本部自身も振り返り（honbu-retro）を行う。
- 各PJは、作業の最後に判断待ちの一覧（12-14 の形）を本部に送る。

### 12-14. 帰ってきたら本部で全部決める（2026-11-26 ユーザー指示）
ユーザーは、帰ってきたら（「戻った」など）本部チャット1つで、全PJの判断を済ませる。
- **各PJ→本部**：判断待ちを、次の形で送る。
  - 番号（PJ内で通し）
  - 何を決めるか（1文）
  - 選択肢 ①②（おすすめは①）
  - 選ぶと何が起きるか（何を・誰に・いくら）
  - 元に戻せるか
  - 期限（あれば）
- **本部→ユーザー**：全PJの判断待ちを、急ぎを先にして、PJごとに1つの番号つきの一覧にする。「全部①」「5だけ②」で答えられる形にする。
- **本部→各PJ**：答えは、ユーザーの言葉のまま、日時と問いの番号を付けて届ける。例：「平尾さんが本部チャットで『全部①、5だけ②』と答えた（2026-11-27 08:10）。あなたの問い 3 → ①」。
- **各PJ**：この形で本部から届いた答えは、ユーザーの答えとして扱い、聞き直さない（2026-11-25 の「各PJのチャットで直接もらう」は、この形に置き換えた）。
  - 元に戻せない操作（外部への公開・第三者への送信・支出・契約・消す）は、届いた問いと答えに対象（何を・誰に・いくら）が入っているときだけ進める。入っていなければ、そのPJのチャットで1回だけ聞く。
  - そのPJの Claude の安全の決まりで、本人がそのチャットで言う必要がある操作は、そう伝える。そのうえで、一言で済むところまで用意して聞く。
  - ログイン・パスワード・認証コードは、これまでどおりユーザー本人が入れる。
- 届いた答えで行ったことは、コミット番号を付けて本部に一言返す（L20）。本部は番号を確かめてからユーザーに伝える（L19）。
