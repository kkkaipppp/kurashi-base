# ADR-002 大きなバックアップと復元の上限（RAID R-08・o31 D037/X006）

- 状態：**提案**（2026-11-27。比べて案を出すところまで。実装は平尾さんの OK の後）
- きっかけ：平尾さんの答え（本部経由、2026-11-27 朝）「3 復元の上限＝① 分割バックアップを ADR で比べる」

## 問題
- 復元は 20MB を超えるファイルを読まない（`app/src/app/settings/page.tsx` の `MAX_BACKUP_BYTES`）
- 自分用（IndexedDB）は記録の量に上限がなく、書き出しに上限もない。合成データで 10万件 23MB・25万件 57.65MB（`docs/design/o29/PERF_RESULT.md`。Node で測った値、iPhone 実機では未確認）
- そのため「書き出せても戻せない」バックアップができうる。iPhone アプリの自動バックアップも同じ形なので、同じ上限にかかる
- 公開版は localStorage（端末でおよそ 5MB）なので、20MB に届かない。**自分用だけの問題**
- 今の実データは上限よりずっと小さい（1人の家計と予定は年に数千件ほど。20MB はおよそ 8万件）。急ぎではない

## 守ること（どの案でも）
1. **書き出せたファイルは、同じアプリで必ず戻せる**（上限は書き出しと復元で同じ値を使う）
2. 復元は、今までどおり検査・プレビュー・追加／置き換えの選択・チェックサムを通す。途中で失敗したら今のデータを変えない
3. 保存の形式（schemaVersion 2）は変えない。今あるバックアップはそのまま読める
4. npm のパッケージは足さない

## 比べた案
| 案 | 内容 | 良い点 | 悪い点・リスク |
|---|---|---|---|
| A 分割のバックアップ | 大きいときは年ごと（または種類ごと）に複数のファイルに分けて書き出し、復元は全部の束を選んで1回で戻す | 1ファイルは小さいまま。iPhone のメモリの心配が少ない | 一部のファイルだけ戻す・足りないまま戻す、という新しい失敗の道ができる（束の ID・枚数・全体のチェックサムが要る）。年をまたぐ記録（固定費・目標・旅行）の分け方を決める必要。自動バックアップの「新しい14個」の数え方も変わる。作る量と試験が最も多い |
| B 上限を上げる（自分用だけ） | 自分用の上限を 20MB→例えば 64MB に。書き出しのときに大きさを見て、上限に近ければ知らせる | 変更が小さい（定数と案内）。形式も手順も今のまま | 58MB の JSON を iPhone の WebView で一度に読むとメモリが足りるかは**未確認**（実機の試験が先）。将来さらに増えれば同じ問題が戻る |
| C 圧縮する | 書き出しを gzip（ブラウザ標準の CompressionStream）で圧縮。JSON は 1/5〜1/8 ほどになる見込み | ファイルが小さく、受け渡しが楽 | 読むときは解いたあとの大きさをメモリに持つので、B と同じメモリの問題は残る。古い Safari での対応の確認が要る。人の目で中身が読めなくなる |
| D 書き出しで止める・知らせるだけ | 上限を超える書き出しのときに「戻せない大きさです」と知らせる | 最も小さい | 書き出しを止めると記録を守る手段が減る（止めるのは不可）。知らせるだけでは戻せないことは変わらない |

## 提案
- **今は B（＋D の知らせ）を先にする**：自分用だけ上限を上げ、書き出しのときに大きさを見せて、上限の 8 割を超えたら知らせる。上限の値は、iPhone 実機で大きな合成データの復元を試してから決める（実機の試験が通るまで上限は 20MB のまま）
- **A（分割）は、実データが上限の半分を超えたら作る**。作るときは「束の ID・枚数・全体のチェックサムがそろわないと戻さない」を最初の試験にする
- C は A・B のどちらとも組み合わせられる。単独では上限の問題を解かないので、今はしない
- どの案も、上の「守ること」1〜4 を試験にしてから入れる

## 決めること（平尾さん）
1. B を先にして、A は実データが増えたときにする（おすすめ）
2. 最初から A（分割）を作る

## 未確認
