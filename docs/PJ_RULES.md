## セッションの終わり（5分）
0. 最後の返信（まとめ欄・本文）が日本語になっているかを確かめる（LESSONS L-09）
1. **今日、ユーザーに直されたこと・手戻りはあったか？** あれば先に、プレイブック 9-2 を済ませる：原因を2〜3段掘る → 次のセッションが読む場所（このファイル・テスト・チェックリスト）を直す → 確かめ方を1つ付ける → `docs/LESSONS.md` に1行 → ユーザーに「次から〇〇します（△△に書きました）」
2. `docs/STATE.md` を更新
3. 決めたことを `docs/DECISIONS.md`、起きたこと・リスクを `docs/RAID.md` に
4. `cd app && npm run check` を通す（落ちたまま終えない。落ちたら正直に書く）
5. `py -3 -I tools/progress.py sync` を実行する。WBS・ロードマップ・論点から、進捗の画面（`docs/progress/PROGRESS.html`）と本部への報告（`portfolio/report.json`・`details.json`）が作り直され、親フォルダ `00_全体進捗/暮らしベース/` に同期される。そのあと本部の検査（`tools/report_check.py` と `../00_経営管理/scripts/details_check.py`）に通す
6. 最後の返信で、sync が出す「WBS の変化」と「本部への報告」（今いるマイルストン・完了数・次の作業・判断待ち）を平尾さんに伝える

## WBS・ロードマップ・論点の更新（2026-11-22 平尾さんの指示）
- **本部への進捗報告は、ロードマップ（`docs/progress/ROADMAP.md` のマイルストン）と WBS をもとにする。** report.json を手で書かない（mode・quality・金額だけは人が決める）
- 作業が終わった・始めた・止まったら、**その都度** `py -3 -I tools/progress.py set <ID> <状態> "根拠"` で WBS を更新する。新しい作業は WBS.csv に行を足す（Start・End を入れる。未完了の日付は仮の予定）
- 決めること（要件・公開・範囲）が出たら `docs/progress/ISSUES.csv` に論点として足す。決まったら「状態＝決定」と「決定」に日付と決めた人を書き、`docs/DECISIONS.md` にも残す
- 更新したら sync して、変わったところを返信で報告する

## 守ること（安全・承認。指摘を理由に緩めない）
- `00_受領資料/` と `docs/ux-autonomous/`・`docs/autonomous_pack/`（受領資料）は書き換えない
- `00_経営管理` とほかのPJのフォルダには書き込まない（例外：ユーザー指示の `../00_全体進捗/暮らしベース/` への進捗同期）
- 外部の有料API・秘密鍵・外部送信はしない。npm パッケージを足すときは、何を入れるかを先に伝える
- git の push・公開・本番配布は、ユーザーの OK をもらってから
- ユーザーのデータ（localStorage）を消す・形式を互換性なく変える変更はしない。形式を変えるときは `schema.ts` の `migrate()` とテストを先に書く
- テスト未実施を PASS と書かない。実機で見ていないものは「実機は未確認」と書く

## UX の基準
- 「前のやつ」「以前の画面」は、旧『くらしカレンダー』の画面イメージ・操作感を指す（Phase 1 ではない）。参考画面：`docs/ux-autonomous/reference_ui/` の4枚。画面を大きく変える前に見比べる（LESSONS L-05）
- 体験の原則：起動して3秒で「今日の予定」と「今月あと使える」が分かる／主要な記録は1〜2操作／予定とお金を同じカレンダーで見る／振り返りで気づきが得られる
- 使えない機能（OCR・同期・AI・共有・ウィジェット）を、使えるように見せない

## 文言チェック（選択肢・ラベルを足すとき。LESSONS L-04）
1. 選択肢は同じ種類・同じ粒度・同じ形の言葉で並べる。種類が違えばグループに分ける
2. 欄の名前：物は「名前」、タスク・目標は「内容」、メモ・予定は「タイトル」
3. チェック欄は短い名詞（完了・達成・上に固定・有効・終日）
4. 任意の欄は `optional` の印（ラベルに「（任意）」と書かない。テストで検査）
5. 画面名は短い名詞。正式名は説明文へ。メニューは中身の種類で分け、状態（準備中）はグループにしない
詳しいルールと修正の履歴：`docs/JAPANESE_COPY_AUDIT.md`

## 確認の手順
- 自動：`cd app && npm run check`（型・lint・テスト・ビルド）
- 画面：アプリ内ブラウザでモバイル幅（375px）。全画面を 320/375/390px で横はみ出しなし
- **iPhone 実機でしか出ない問題がある**（日付・時刻の欄、キーボード、http での制限。LESSONS L-01〜03）。入力部品やシートを変えたら、実機での確認をユーザーに頼む。直したら「実機で直ったか」まで確かめて完了にする（L-08）
- 画面確認で入れたテスト用データは、確認のあと必ず消す

## iPhone 用サーバー（同じ Wi-Fi の中だけ。LESSONS L-07）
1. `cd app && npm run build`（`npm run check` に含まれる）
2. ポート 3211 を使っているプロセスを止める（タスクを止めても残ることがある）
3. `cd app && npx next start -H 0.0.0.0 -p 3211` をバックグラウンドで起動
4. `curl` で `http://<PCのIP>:3211/` と新しい画面が 200 になるか確かめる
5. iPhone で開けない（黒い画面のまま）ときは、iPhone の Wi-Fi を **XN-002-5G** にする。XN-002（2.4GHz）では端末どうしがつながらないことがある（LESSONS L-10）

## ユーザーへの頼み方（プレイブック 7章・10章 L1/L2）
- **ユーザーへの返信は、まとめ欄（wrap_up）も本文も日本語で書く**（全体の CLAUDE.md の決まり。LESSONS L-09）
- Claude ができることは自分でやる。ユーザーに頼むのは、iPhone の実機操作・判断・公開や送信の最終確認だけで、1回にまとめる
- 実機確認を頼むときは、**1行目に開く URL だけ**を書く（LESSONS L-06）
- 選択肢には①②③の番号を付け、推奨を①にする。判断は1回に1つ
- 「できました」は証拠（テスト・画面・実機）とセットで
- 「前のやつ」「以前の版」など、どれを指すか分からない言葉が出たら、どの版・どのファイルかを①②③で確かめてから作業する（プレイブック L10・LESSONS L-05）
