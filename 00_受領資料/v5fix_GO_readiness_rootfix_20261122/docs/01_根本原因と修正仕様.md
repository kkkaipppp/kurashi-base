# 1. 根本原因・解決方針（基準コミット a6e7f00）

## G-P0-01：「すべて削除」でアプリ内の保存情報が残る
- 現状：`app/src/lib/store.tsx:215-218` は本体データを空に更新した後で `clearUndo()` を呼ぶ。`app/src/lib/storage.ts:165-182` の `clearUndo()` は削除エラーを無視し、`kurashi-base:corrupt:*` を対象外にしている。
- 根本原因：アプリが扱う保存キーが一覧化されておらず、複数キー削除の成功条件も定義されていない。
- 対応：本体、undo、退避分を列挙し、残存チェック後にだけ成功とする `wipeAllAppData` を導入。**他サービスのキーには触れない**。削除途中の例外では可能な範囲で巻き戻す。巻き戻せない場合も黙って成功としない。
- 例外：localStorageは複数キーを同時に確定するトランザクションを持たない。完全な原子性は保証できない。これを「テストで100%保証した」と主張しない。

## G-P0-02：同じ予定を別タブで編集すると古い入力で上書きする
- 現状：`app/src/lib/store.tsx:161-165` の `updateEvent` は現在ストアの予定に新しい入力を無条件適用する。`EventSheet.tsx:217-238` で編集内容の初期値を固定しても、編集開始時の元の予定との一致チェックがない。
- 根本原因：全体データの競合検出があっても、入力フォームが開いている間にそのレコードが変わったことをチェックしない。
- 対応：フォームを開いた時の予定JSONを保持し、保存直前に対象予定と比較。異なれば保存を中止し、ユーザー入力を残して最新の予定の開き直しを求める。**変更した項目を黙ってマージしない。**
- 拡張：同一取引・旅行・タスク・契約・資格などの更新にも同じ競合ガードを展開する。特に取引金額・口座残高に関係する保存を優先。

## G-P0-03：復元と取り消しの失敗復旧
- 現状：`app/src/lib/storage.ts:116-163` では、undo控えを先に書き、保存に失敗したら元の控えを復旧する処理がある。ただし複数タブ同時利用、容量不足、強制終了の競合は完全には排除できない。
- 対応：`saveWithUndo` の再現テストを増強。「undo書込失敗」「本体書込失敗」「undo復旧失敗」「外部更新割込み」「JSON不正・旧形式」「取り消し再実行」の全経路に失敗時の後始末と説明を入れる。重要な復元前にはバックアップ書き出しの案内を優先する。
- 受入：復元に失敗しても本体が読める、誤った成功表示が出ない。undoが壊れた場合に無理やり戻さない。

## G-P0-04：iPhone実機と公開URLが未検証
- 現状：最終修正後のiPhone Safariで「予定の任意項目削除→再起動」「バックアップ→復元→取り消し→やり直し」は未実施。追加Vitestでは代替できない。
- 対応：証拠（スクリーンショット・手順・実施日時・OS・URL・結果）を残す。ユーザーデータではなく匿名のテストデータを使う。プレビューURLと本番URLは別の保存領域なので、テスト時に誤解しない。

## G-P1-01：本人にとってのデータの安全説明
- 現状：localStorage上で端末/ブラウザ単位で保存。別端末には引き継がれない。Safari等で消える可能性がある。
- 対応：初回1画面の案内を短くする。「データはこのブラウザに保存されます」「週に1回バックアップ」の2文と、ワンタップ導線。保存成功とダウンロード開始を混同しない。

## 追加で留意する未解決の限界
- `saveDataIfUnchanged` は読み取り→書き込みの非原子的な処理であり、極めて近いタイミングでの2タブ同時書き込みを完全には排他できない。
- 資産・資格・健康等は敏感な記録を含み得る。第三者に同一ブラウザを貸すケースと、バックアップJSONの共有に注意。
- これらは友人1人・1週間のβで即クラウドDBを必須とする理由ではないが、正式販売時には設計課題として扱う。
