【くらしベース / 友人1人・1週間β版を客観的にGOへ進める 自律開発指示】

現在の開発ブランチ beta/friend-v1、基準コミット a6e7f00 に対し、添付の「くらしベースGO達成パック」を展開して全文を確認し、実際の実装・テスト・修正・進捗更新を自律的に実施してください。ユーザーが途中離席していても、安全な開発判断のために確認を求めず進行してください。

製品の目的：予定とお金を起点に暮らしを一か所で管理し、毎日3秒で状況が分かり、1〜2操作で記録を始められること。初めて使う友人が説明なしで利用できること。現行ブランド「くらしベース / KURASHI BASE」、画面の基本設計、storage key `kurashi-base:data:v1` と schemaVersion 2 を維持。旧データの破壊や強制移行をしない。一般販売向けクラウドDBは今回勝手に導入しない。

【実施順】
1. `README_最初に.md` と `docs/01`〜`06` を熟読。まずコミットとバックアップを作成し、作業ブランチを作る。
2. `patches/01_*.patch` を `git apply --check` で確認。原本が異なる場合は丸ごと上書きせず、意味のある差分だけを反映する。`patches/eventConcurrency.ts` と `tests/go-data-deletion.test.ts` も適切な場所へ配置。**テストが修正前に失敗し、修正後に通るRED→GREENを確認する。**
3. 保存データ消去の根本修正：本体・取り消し控え・退避データすべての削除、削除結果の検証、失敗時の復旧・報告。他アプリのlocalStorageには絶対に触れない。
4. 同じ予定を2タブで編集した場合、古い入力で新しい変更を黙って上書きしない。取引・旅行・タスクなども同様の競合から守る。不具合の修正と実行テストを優先。
5. 既存のバックアップ、追加復元、旅行・資格・v1/v2移行、NISA計算、振り返り等を壊さず回帰確認。失敗系は容量不足、JSON破損、途中例外、2タブを含める。
6. ユーザーが誤って自分のデータを消さないよう、保存失敗時の案内を見直す。「サイトデータを消す」と軽々しく誘導せず、まず既存データのバックアップを書き出す。ホーム・予定詳細・バックアップの説明を読みやすい日本語に修正。
7. `cd app && npm ci && npm run check` で型・lint・Vitest・ビルド。テストに名前だけ追加して、実動作未検証のまま合格にしない。必要ならPlaywright等で自動テストを追加。ただし実機証拠が必要な箇所は別にする。
8. 起動中のアプリを実操作し、主要画面のスクリーンショットを最新コミットで撮影してレビュー。友人の最初の60秒に不要な説明・迷うボタン・長文を減らす。
9. `docs/02_必須受入シナリオ.md` B01〜B15を実施し、証拠を `docs/release/` に保存する。iPhone実機でのバックアップ/復元/undo/redoやキーボード操作は実際のiPhoneで確認しなければPASSとしない。Claudeに実機が無ければ、具体的な1枚の操作手順とNOT_RUNを残す。
10. GitHub Private推奨、Vercelプレビューや公開先の準備はしてよいが、ユーザーの承認なしに本番配信・課金・個人データの破壊的操作を行わない。URLは明示的に区別する。アプリの外部公開は別途承認を得る。
11. `docs/06_WBSと改善順序.md` の進捗を更新し、親フォルダの管理台帳も利用できれば同期する。作業完了時は実装差分、RED→GREEN、テスト件数、残るNOT_RUN、公開GO/NO-GO理由、URLの公開状況、巻き戻し方法を報告する。

【GO判定の原則】
「条件付きGO」を無理やりGOに言い換えない。フルビルド、B01〜B15の客観的証拠、最終修正後のiPhone実機、公開URLでの安全確認が全部揃った時だけ、**友人1人・1週間のβ版としてGO**。未実施ならNO-GOのまま明示。完璧な無故障や販売品質を証明したとは書かない。

目的は計画書を増やすことではない。コードと体験を実際に直し、出せる証拠が揃うところまで自律的に進めること。以上。
